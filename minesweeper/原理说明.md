# 扫雷 · 原理说明与尺寸建议

## 一、文件结构与运行

| 文件 | 作用 |
| --- | --- |
| `index.html` | 页面结构：难度按钮、计数器、笑脸、棋盘容器 |
| `style.css` | 现代深色风格外观与动画，格子大小由 CSS 变量 `--cell`、间距由 `--gap` 控制 |
| `game.js` | 全部游戏逻辑：布雷、计数、展开、插旗、胜负判定、计时 |

运行方式：直接双击 `index.html` 用浏览器打开即可，不需要服务器和任何依赖。

操作方式：

- 左键：翻开格子
- 右键：插旗 / 取消插旗
- 点击已翻开的数字（或鼠标中键）：若周围旗数等于该数字，自动翻开其余邻格（俗称"双击"或 chord）
- 手机：点按翻开，长按 0.4 秒插旗
- `R` 或 `F2`：重新开始

## 二、核心原理

### 1. 数据模型

棋盘是 `rows × cols` 的网格，用一维数组存储，下标 `i` 与坐标的换算为：

```
行 r = Math.floor(i / cols)
列 c = i % cols
i   = r * cols + c
```

每个格子保存 4 个字段：

```js
{ mine: false, adjacent: 0, revealed: false, flagged: false }
```

- `mine`：是否是雷
- `adjacent`：周围 8 格中雷的数量（即显示的数字）
- `revealed`：是否已翻开
- `flagged`：是否已插旗

### 2. 每局随机生成（重点）

每一局的雷位置都是重新随机生成的，具体做法分三步：

**(1) 延迟布雷：第一次点击之后才布雷**

开局时棋盘上没有任何雷。玩家第一次点击某格时，才以这一格为中心，把它和周围 8 格（共 9 格）设为"安全区"，再在安全区之外布雷。

这样做的好处：

- 第一步永远不会踩雷；
- 第一步点到的一定是 0，会自动展开一片区域，开局就有可推理的信息；
- 雷的位置取决于"随机数 + 玩家第一下点在哪"，每局都不同。

**(2) 部分 Fisher–Yates 洗牌**

把安全区以外的所有格子编号放进候选数组 `candidates`，然后只洗前 `mines` 个位置：

```js
for (let i = 0; i < mines; i++) {
  const j = i + randomInt(candidates.length - i);  // 从剩余部分随机挑一个
  swap(candidates[i], candidates[j]);
  cells[candidates[i]].mine = true;
}
```

这种算法保证：

- 每一种"从 N 个候选格里选 M 个放雷"的组合出现概率完全相等（均匀分布）；
- 不会重复选中同一个格子，不需要"随机到重复就重试"；
- 时间复杂度 O(N)，即使 30×50 的大棋盘也瞬间完成。

> 常见的错误写法是"随机选一个格子，如果已有雷就再选"，雷很多时会反复撞车变慢；
> 或者 `array.sort(() => Math.random() - 0.5)`，这种写法分布并不均匀。

**(3) 使用加密级随机数**

`randomInt(max)` 使用浏览器的 `crypto.getRandomValues()`，比 `Math.random()` 更难预测；
并且使用"拒绝采样"去掉取模偏差：

```js
const limit = Math.floor(2^32 / max) * max;
do { x = 随机32位整数 } while (x >= limit);   // 超出整倍数范围的丢弃重抽
return x % max;
```

如果直接 `x % max`，当 2³² 不能被 `max` 整除时，较小的数会略微更容易出现，拒绝采样可以消除这一点。

### 3. 计算数字

布雷完成后遍历每个格子，统计周围 8 个邻居（边角格子邻居更少）中雷的数量，写入 `adjacent`。
`neighbors(i)` 函数负责返回合法的邻居下标，自动处理越界。

### 4. 自动展开（Flood Fill）

点到数字为 0 的格子时，周围必然没有雷，可以把邻居全部翻开；如果邻居也是 0，继续向外扩散。

实现上使用**栈 + 循环**而不是递归：

```js
const stack = [起点];
while (stack.length) {
  const k = stack.pop();
  if (已翻开或已插旗) continue;
  翻开 k;
  if (k 的数字为 0) 把 k 的所有未翻开邻居压入栈;
}
```

用循环是为了避免大棋盘上递归层数过深导致"栈溢出"。

### 5. 快速翻开（Chord）

点击一个已翻开的数字 `n`，如果它周围恰好插了 `n` 面旗，就把其余未插旗的邻居全部翻开。
若旗子插错了，这一步会翻到雷导致失败——和原版 Windows 扫雷的规则一致。

### 6. 胜负判定

- **失败**：翻开了一个雷。此时显示所有雷，踩中的雷标红，插错的旗显示 ❌。
- **胜利**：已翻开的格子数 = 总格数 − 雷数。也就是说，**胜利只需要翻开所有安全格，不要求把雷全部插旗**。胜利后自动给所有雷插上旗。

### 7. 计时与最佳成绩

- 第一次点击时开始计时，胜利或失败时停止；
- 每种"行×列+雷数"配置分别在 `localStorage` 中保存最快成绩，刷新页面后仍然保留。

### 8. 关于"需要猜"的局面

本游戏采用纯随机布雷（和 Windows 原版一样），因此**少数局面可能无法完全靠逻辑推出，必须猜一次**，
典型例子是角落里的"50/50"。这是随机扫雷的固有特性，不是 Bug。
雷密度越高，出现需要猜的局面概率越大（见下文）。

如果想要"保证无需猜测"的版本，需要在布雷后运行一个求解器模拟推理，推不下去就重新生成，实现复杂度和生成耗时都会显著增加。

## 三、多少尺寸合理

### 1. 决定难度的关键：雷密度

```
雷密度 = 雷数 ÷ 总格数
```

棋盘大小主要影响"一局要玩多久"，而**雷密度才真正决定难度**。

| 雷密度 | 体验 |
| --- | --- |
| < 10% | 太简单，大片自动展开，几乎不需要推理 |
| 12% – 16% | 舒适，适合入门到中级 |
| 16% – 21% | 有挑战，需要较多推理（高级难度在这里） |
| 21% – 25% | 很难，经常需要猜 |
| > 25% | 大量死局，几乎全靠运气，不推荐 |

### 2. 经典三档（推荐直接使用）

这三档来自 Windows 原版扫雷，经过了几十年验证，是最平衡的配置：

| 难度 | 尺寸（行×列） | 雷数 | 雷密度 | 适合 |
| --- | --- | --- | --- | --- |
| 初级 | 9 × 9 | 10 | 12.3% | 新手、手机竖屏 |
| 中级 | 16 × 16 | 40 | 15.6% | 大多数玩家 |
| 高级 | 16 × 30 | 99 | 20.6% | 熟练玩家、电脑横屏 |

### 3. 按屏幕选择尺寸

格子太小会点错，建议：

- **电脑（鼠标）**：每格 ≥ 24px 比较舒适，最小不要低于 20px；
- **手机（手指）**：每格 ≥ 32px，否则很容易误触。

本游戏会根据窗口大小自动把格子缩放到 20px – 36px 之间，放不下时棋盘区域可以滚动。

估算方法：`可放列数 ≈ 屏幕可用宽度 ÷ 格子大小`。

| 设备 | 可用宽度（约） | 推荐尺寸 |
| --- | --- | --- |
| 手机竖屏（宽 375–430px） | 340px | 9×9（每格约 36px），最多 10 列 |
| 平板 / 小笔记本 | 900px | 16×16、16×30 |
| 1080p 显示器 | 1400px | 16×30，自定义最大可到 24×50 左右 |
| 2K / 4K 显示器 | 更宽 | 30×50 也能舒适游玩 |

### 4. 自定义模式的限制及原因

| 参数 | 范围 | 原因 |
| --- | --- | --- |
| 行数 | 5 – 30 | 少于 5 行没有可玩性；超过 30 行在 1080p 屏上即使 20px 格子也放不下 |
| 列数 | 5 – 50 | 50 列 × 24px ≈ 1200px，是常见显示器能完整显示的宽度 |
| 雷数 | 1 – (行×列 − 9) | 必须留出首次点击的 9 格安全区 |

自定义时推荐雷数公式：

```
推荐雷数 ≈ 行 × 列 × 0.12 ～ 0.21
```

例如 20 × 24 = 480 格，推荐 58 – 101 个雷；输入框下方会实时显示当前密度和推荐范围。
